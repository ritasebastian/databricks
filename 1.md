# Delta Table in Databricks — Complete Guide with SQL and PySpark Examples

A Delta table is a table that stores data using the Delta Lake format. Delta Lake extends Apache Parquet with a transaction log, allowing Databricks to reliably read, insert, update, delete, and track changes to data.

Delta Lake is the default table format in Databricks.&#x20;

I'll use a simple `transactions` table throughout the examples.

## 1. What is a Delta table?

A traditional Parquet dataset stores data in files. A Delta table stores data in Parquet files plus a transaction log that records which files make up each committed version of the table.

## 2. Important features of Delta Lake

| Feature                | Explanation                                    |
| ---------------------- | ---------------------------------------------- |
| ACID transactions      | Ensures reliable data operations               |
| Time Travel            | Query previous versions of a table             |
| MERGE (Upsert)         | Update existing records and insert new records |
| UPDATE / DELETE        | Modify or remove records                       |
| Schema Enforcement     | Prevent incompatible data from being written   |
| Schema Evolution       | Allow controlled changes to table schema       |
| Change Data Feed (CDF) | Track row-level changes                        |
| Structured Streaming   | Support incremental reading and writing        |
| OPTIMIZE               | Improve data file layout and query efficiency  |
| VACUUM                 | Remove obsolete data files after retention     |

These capabilities are particularly useful in production ETL pipelines.&#x20;

## 3. Create a Delta table

Let's create an example table containing payment transactions.

### SQL

```
CREATE TABLE main.default.transactions (
    txn_id INT,
    customer_id STRING,
    amount DOUBLE,
    status STRING,
    txn_date DATE
)
USING DELTA;
```

### PySpark

```
data = [    (101, "C001", 150.0, "SUCCESS"),    (102, "C002", 200.0, "SUCCESS"),    (103, "C003", 50.0, "FAILED")]columns = [    "txn_id",    "customer_id",    "amount",    "status"]df = spark.createDataFrame(data, columns)df.write.format("delta") \    .mode("overwrite") \    .saveAsTable("main.default.transactions_demo")
```

The Python example creates a separate demonstration table without the `txn_date` column.

## 5. Insert, update, and delete records

These commands demonstrate how Delta tables support modifications.

### INSERT — Add new records

```
INSERT INTO transactions
VALUES (
    104,
    'C004',
    350.0,
    'SUCCESS',
    DATE '2026-11-10'
);
```

### UPDATE — Modify existing records

```
UPDATE transactions
SET amount = 500
WHERE txn_id = 101;
```

### DELETE — Remove existing records

```
DELETE FROM transactions
WHERE txn_id = 103;
```

Unlike writing directly to ordinary Parquet files, Delta provides transactional table operations for updates and deletes.

## 6. MERGE INTO — Upsert

`MERGE INTO` is one of the most important commands for Databricks data engineers.

MERGE means insert new rows and/or update existing rows based on a matching condition.

Suppose your target table contains:

| txn_id | amount | status  |
| ------ | ------ | ------- |
| 101    | 150    | SUCCESS |
| 102    | 200    | PENDING |

New incoming data:

| txn_id | amount | status  |
| ------ | ------ | ------- |
| 102    | 250    | SUCCESS |
| 103    | 300    | SUCCESS |

We want to update transaction 102 and insert transaction 103.

```
MERGE INTO transactions AS target
USING new_transactions AS source
ON target.txn_id = source.txn_id

WHEN MATCHED THEN
    UPDATE SET
        target.amount = source.amount,
        target.status = source.status

WHEN NOT MATCHED THEN
    INSERT (
        txn_id, amount, status
    )
    VALUES (
        source.txn_id,
        source.amount,
        source.status
    );
```

Result (showing these three columns):

| txn_id | amount | status  |
| ------ | ------ | ------- |
| 101    | 150    | SUCCESS |
| 102    | 250    | SUCCESS |
| 103    | 300    | SUCCESS |

In this example, `new_transactions` must be an existing source table or view. The source should have unique `txn_id` values for deterministic matching.

For a real table containing additional required columns, include those columns in the insert as well.

## 7. Time Travel — Read old versions of a Delta table

This is one of Delta Lake's most useful features.

Each successful write creates a new table version, allowing you to query historical data while the required history and data files are retained.

Example:

1. Version 0 — Table created

   Original transactions inserted
2. Version 1 — UPDATE executed

   Transaction 101 amount changed
3. Version 2 — DELETE executed

   Transaction 103 deleted

### View Delta table history

```
DESCRIBE HISTORY transactions;
```

### Read version 0

```
SELECT *
FROM transactions VERSION AS OF 0;
```

### Read version 1

```
SELECT *
FROM transactions VERSION AS OF 1;
```

### Read a previous timestamp

```
SELECT *
FROM transactions
TIMESTAMP AS OF '2026-11-09 10:00:00';
```

### Restore a previous version

```
RESTORE TABLE transactions
TO VERSION AS OF 0;
```

`RESTORE` changes the current table state to the historical version and creates a new version rather than simply deleting the subsequent history.

Important: Time Travel does not guarantee unlimited history. Old data files can be deleted by `VACUUM`, making older versions unreadable.

## 8. Delta table write modes

| Mode            | Meaning               | Example                        |
| --------------- | --------------------- | ------------------------------ |
| `append`        | Add records           | Daily transactions             |
| `overwrite`     | Replace existing data | Rebuild a reporting table      |
| `ignore`        | Skip if table exists  | Conditional initial creation   |
| `errorifexists` | Fail if table exists  | Prevent accidental replacement |

### PySpark example

```
df.write.format("delta") \    .mode("append") \    .saveAsTable("transactions")
```

Exam point: Append mode does not automatically check for duplicate transaction IDs. Use `MERGE` or another deduplication strategy when records need to remain unique.

## 9. Managed Delta table vs External Delta table

Databricks supports managed and external Delta tables.

| ------------------- | ----------------------------------------------------------------------- | -------------------------------------------- |
| Storage location    | Managed by Unity Catalog                                                | Specified by user                            |
| Metadata management | Unity Catalog                                                           | Unity Catalog                                |
| Data lifecycle      | Databricks-managed                                                      | Externally managed                           |
| DROP TABLE          | Removes table and associated managed data, subject to recovery policies | Removes metadata, preserves external files   |
| Recommended         | Most Databricks workloads                                               | Data requiring independently managed storage |

## 10. Schema Enforcement and Schema Evolution

These are two different concepts.

Schema Enforcement: Delta checks whether data being written matches the target table schema.

Suppose the table expects:

| Column | Data type |
| ------ | --------- |
| txn_id | INT       |
| amount | DOUBLE    |

An incoming DataFrame with incompatible values or an unexpected schema may cause the write to fail, preventing accidental schema changes.

Schema Evolution: Delta can allow new columns to be added during a write when configured appropriately.

Example:

```
df.write.format("delta") \    .mode("append") \    .option("mergeSchema", "true") \    .saveAsTable("transactions")
```

If `df` contains a new column such as `payment_method`, Delta can add it to the target table schema.

Schema evolution does not mean all incompatible data types are accepted.

## 11. Change Data Feed (CDF)

Change Data Feed is a Delta Lake feature that allows downstream processes to identify row-level changes.

### Enable CDF

```
ALTER TABLE transactions
SET TBLPROPERTIES (
    delta.enableChangeDataFeed = true
);
```

When enabled, subsequent changes can be read using the CDF interface.

CDF records can have these change types:

| Change type        | Meaning           |
| ------------------ | ----------------- |
| `insert`           | New record        |
| `delete`           | Deleted record    |
| `update_preimage`  | Row before update |
| `update_postimage` | Row after update  |

### Read CDF changes with SQL

```
SELECT *
FROM table_changes('transactions', 1);
```

Here, `1` is an example starting version. It must be a version at which CDF was enabled and whose required history remains available.

### Read CDF using PySpark

```
cdf_df = (    spark.read    .format("delta")    .option("readChangeFeed", "true")    .option("startingVersion", 1)    .table("transactions"))display(cdf_df)
```

CDF is especially useful for SCD Type 1, SCD Type 2, and incremental pipelines.

## 12. Delta Lake with Structured Streaming

Delta tables support both batch and streaming operations.

### Batch read

```
df = spark.read \    .format("delta") \    .table("transactions")
```

### Streaming read

```
df = spark.readStream \    .format("delta") \    .table("transactions")
```

### Streaming write

```
query = (    df.writeStream    .format("delta")    .outputMode("append")    .option(        "checkpointLocation",        "/Volumes/main/default/checkpoints/txns"    )    .toTable("transactions_silver"))
```

This streaming example assumes an append-only source. Updates and deletes in the source need additional handling, such as CDF.

## 13. OPTIMIZE vs VACUUM

These two commands are very important for Databricks certification.

| Feature                     | OPTIMIZE                  | VACUUM                           |
| --------------------------- | ------------------------- | -------------------------------- |
| Purpose                     | Improve file layout       | Remove obsolete data files       |
| Main benefit                | Improve query performance | Reclaim storage                  |
| Removes current table rows? | No                        | No                               |
| Affects Time Travel?        | Preserves logical history | Can make old versions unreadable |

### OPTIMIZE

```
OPTIMIZE transactions;
```

This can combine smaller data files into larger, more efficient files.

### VACUUM

```
VACUUM transactions;
```

Removes eligible obsolete data files.

The default retention threshold is 7 days, but that does not mean every table is guaranteed to support seven days of Time Travel. History retention settings also matter.&#x20;

## 14. ACID transactions in Delta Lake

ACID makes Delta tables reliable for production processing.

| Property        | Meaning                               | Example                                             |
| --------------- | ------------------------------------- | --------------------------------------------------- |
| A — Atomicity   | All-or-nothing operation              | A failed transaction does not partially commit      |
| C — Consistency | Maintains defined table rules         | Writes must respect enforced schema and constraints |
| I — Isolation   | Concurrent operations are coordinated | Readers see a consistent committed table state      |
| D — Durability  | Committed data persists               | Completed transactions survive failures             |

Note that ACID does not automatically enforce uniqueness of `customer_id` or `txn_id`. Databricks primary-key declarations are generally informational rather than enforced.&#x20;

## 16. Delta Lake vs Parquet

| Feature                 | Plain Parquet files        | Delta Lake             |
| ----------------------- | -------------------------- | ---------------------- |
| Data file format        | Parquet                    | Parquet                |
| Transaction log         | No                         | Yes                    |
| ACID transactions       | Not provided by the format | Yes                    |
| UPDATE / DELETE / MERGE | Not native to the format   | Yes                    |
| Time Travel             | Not native                 | Yes                    |
| Schema enforcement      | Limited                    | Yes                    |
| CDF                     | No                         | Yes                    |
| Streaming integration   | Possible                   | Built-in Delta support |
